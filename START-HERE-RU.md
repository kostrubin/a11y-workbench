# A11y Workbench — запуск автономной разработки

Пакет подготовки v1.1 с уточнёнными правилами open source. Само приложение пока не реализовано. Разработка и тестирование должны выполняться в **Codex Cloud**, а не в локальном Codex и не через удалённое управление твоим компьютером.

Владелец подтвердил: `kostrubin/a11y-workbench` остаётся **публичным**. Старое требование приватного репозитория отменено. Проверенные исходники, документацию, тесты и синтетические примеры разрешено сохранять обычными коммитами и push в рабочую ветку без повторных согласований. Видимость репозитория менять не нужно. Перед каждой отправкой проверяй файлы и коммиты; секреты, токены, персональные данные, реальные отчёты и чувствительные логи публиковать нельзя. Сохраняй MIT и обязательные уведомления о лицензиях зависимостей. Не используй force push и не обходи защиту веток.

Это разрешение не включает деплой, публичные preview, GitHub Releases, публикацию пакетов, индексацию сайта или дополнительные расходы. `SITE_RELEASE_APPROVED=false`. Облачная среда остаётся отдельной приватной средой с доступом **Only me**.

## Кратчайший маршрут без локального терминала

1. Используй существующий публичный репозиторий `kostrubin/a11y-workbench` и рабочую ветку. Сначала изучи текущее содержимое и доступ интеграции, не перезаписывай выполненную работу. Не меняй видимость и не используй другие проекты.
2. В Codex выбери **Work in → Cloud → Select environment → Create environment** либо **Settings → Codex Cloud → Environments → Create environment**. Подключи только этот репозиторий. Доступ к среде: **Only me**. При необходимости дай существующей GitHub-интеграции доступ именно к нему.
3. Для подготовки среды используй `SETUP-CLOUD-ENVIRONMENT.txt`. На этом этапе отсутствие `package.json` допустимо. Нужны совместимый Node LTS, npm, Git, Bash и разрешённый доступ к зависимостям во время будущей задачи. Секреты приложения и OpenAI API key не требуются. Публикация проверенной конфигурации приватной среды разрешена. Используй доступное действие **Publish** и проверь результат; сохранённый черновик не считается опубликованной средой. Это не публикация приложения.
4. Начни новую задачу именно в этой среде. Передай один из двух эквивалентных комплектов:
   - **Вариант A:** если актуальные файлы уже есть в рабочей ветке, передай целиком `CODEX-IMPLEMENTATION-PROMPT.txt`. Агент должен прочитать договорённости в этой ветке и выполнить полный промт. ZIP нужен только для отсутствующих seed-файлов, без перезаписи более новой работы.
   - **Вариант B:** передай целиком актуальный самодостаточный промт с файлами seed. Старый внешний файл из исходного ZIP содержит отменённые правила приватности: не используй его для восстановления поверх актуальной ветки. При ограничении размера поля используй вложение с полным актуальным текстом и команду выполнить его.

Не запускай A и B как две параллельные разработки. Не помещай файлы в лишнюю вложенную папку `a11y-workbench/a11y-workbench`. Не настраивай `bash scripts/cloud-setup.sh` до появления этого файла в репозитории.

После реального старта облачной задачи компьютер не должен оставаться включённым. Лимит сессии, квота или запрос разрешения могут всё же остановить работу: промт не предоставляет неограниченное выполнение.

## Дополнительный bootstrap

Рядом с папкой проекта в ZIP расположен `a11y-workbench-bootstrap.py`. Он нужен только как альтернативный способ создать отсутствующие seed-файлы **в выбранном облачном workspace**. Он не требует интернет-доступа и не создаёт GitHub-репозиторий или среду. Сначала проверка без изменений, затем явная запись:

```bash
python3 /path/to/a11y-workbench-bootstrap.py --target /path/to/authorized/repository
python3 /path/to/a11y-workbench-bootstrap.py --target /path/to/authorized/repository --apply
```

Скрипт не перезаписывает отличающиеся файлы, не следует символическим ссылкам и по умолчанию ничего не записывает. Начальный существующий README сохраняется. Не запускай его в другом проекте. Bootstrap исходного ZIP — исторический снимок: не восстанавливай из него отменённые правила приватности вместо актуальных документов репозитория. Путь к материализованному вложению определяет сама облачная сессия; приведённые пути — обозначения, не реальные расположения файлов.

## Настройки и ограничения

- Только синтетические отчёты при разработке. Не загружать рабочие клиентские файлы или секреты.
- Нет оплаты API, покупки кредитов, включения платного CI или автоматического пополнения.
- Не подключать домен, хостинг или автодеплой.
- `SITE_RELEASE_APPROVED=false`, `SITE_PUBLIC_ORIGIN` пустой; `NEXT_TELEMETRY_DISABLED=1` при сборке.
- Решения пользователя: бюджет, границы безопасности, чувствительные данные, релиз. Обычные инженерные решения принимает агент.
- Тесты интерфейса — через установленный Playwright и реально запускаемый браузер. Наличие пакета без browser binary не считается проверкой.

## После остановки

Открой **ту же задачу**, чтобы сохранить её рабочие файлы. Используй `CONTINUE-CLOUD-TASK.txt`. Новый task не обязан содержать предыдущие незакоммиченные изменения. Агент должен сохранять прогресс, журнал решений, результаты проверок и инструкции продолжения.

## Что нельзя считать готовым

GitHub подтвердил существование публичного `kostrubin/a11y-workbench`; прежний ответ 404 из подготовки больше не описывает текущий доступ. Разрешение на публикацию исходников получено. Это не подтверждает публикацию приватной среды или запуск coding task: для них нужны отдельные проверяемые результаты. Никакой черновик и никакое неактивное approval request не считаются запущенной задачей. Приложение, lockfile и браузерные тесты ещё не реализованы; деплой и индексация не разрешены. Актуальные результаты подготовки находятся в `docs/VERIFICATION.md` и `docs/DELIVERY-STATUS.md`.
