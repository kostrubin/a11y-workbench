Run a bounded keyboard review

Review one useful task from its starting state to its outcome. Record what you did and observed so another person can reproduce the same path.

A checklist marked pass without a task, state or observation gives the next reviewer little evidence about what was actually usable.

Define the boundary before you start

Choose a task such as inspecting the synthetic sample and exporting a minimized report. State the browser and operating system you actually used. A keyboard review is not a substitute for a screen-reader session, and a headless browser focus assertion is not a human review.

Begin from a known state. For the workbench, load the sample instead of a real report. For the pattern lab, use the corrected default and its reset control. If you later test a broken variant, record that it was the intentionally broken demonstration.

Follow a repeatable path

Use the keys the control’s semantics call for. Tab is a way through the page; arrow keys have a more local meaning inside widgets such as the action menu.

  1. Use Tab to reach the skip link and enter the main content. Check that focus is visible and not hidden beneath another element.
  2. Reach the file picker or sample action, then move through state and outcome filters without needing a pointer.
  3. Select a finding, read its details and return to the findings list. At a narrow viewport, check that the return action restores useful focus.
  4. Reach a manual check and deliberately choose a status. Supply a concrete local observation or a not-applicable reason.
  5. Inspect the export preview before activating the explicit download action.
  6. Clear the workspace and confirm that the imported findings and local notes disappear. Reload to confirm session data does not return.

Record an observation you can reproduce

A useful synthetic observation might read: “In forms.invalid, submitting two empty fields moved focus to the first invalid field; its visible error described the required value. After correction, the local success message appeared.” That is more informative than “keyboard good.”

If a task fails, record the last successful step, the key pressed and the visible or focused result. Do not include personal data in an observation. Workbench keeps these free-text notes only in the current session and excludes them from P0 exports.

Pass, fail and not-applicable are user-reported manual statuses. A not-applicable selection needs a reason. Importing a minimized status does not restore its omitted observation or independently verify someone else’s claim.

Add the checks this path cannot cover

Repeat important tasks at narrow widths and with reduced motion. Check real browser zoom where available; changing device pixel ratio or CSS zoom is not equivalent to a 200% browser-zoom review.

A separate assistive-technology session should record the actual browser, operating system, screen reader/version and observation. If no session happened, its status is NOT RUN. A zero-violation scan or successful keyboard test cannot fill that entry.

Verify the behavior

Run from the repository root after the documented dependency and browser setup.

npm run test:e2e
npm run test:a11y

Expected evidence: Browser regressions inspect structural focus and keyboard behavior; their results remain separate from user-reported manual observations.

Manual review: Complete the bounded path above and retain a truthful observation. No screen-reader session is claimed by this guide.

These are reproduction instructions, not a claim that a command or human session passed. See the actual verification record for observed results.
