Read an axe result without losing its limits

Start with what was captured. A rule result describes an observation in a particular interface state; it is not a verdict on every page or every person’s experience.

A single rule can affect several controls. Treating its rule count as the number of affected controls hides work, while treating an incomplete result as a pass hides uncertainty.

Read the capture before the finding

Open the supplied sample and select a state such as forms.initial or dialog.open. Read the declared engine version, capture status and scope before interpreting the findings. A closed dialog and an open dialog are different observations, even when they belong to the same page.

The bundled contract sample is hand-authored synthetic data. Its sentinel engine versions explain the comparison rules; they are not evidence that axe scanned this website. A real CLI capture records the installed engine and the states it actually exercised.

  1. Choose a state and check whether its capture is complete, partial or an error.
  2. Read automated outcomes separately from user-reported manual checks.
  3. Select a rule/subject finding and read its safe identifiers, impact and comparison reason.
  4. Open a trusted explanation from the bundled catalog, then reproduce the interaction in the related pattern.

Keep all four outcome categories

The categories answer different questions. Do not add them into an accessibility score.

OutcomeWhat it means hereUseful next action
ViolationThe engine reported a failed automated check.Inspect the rule and affected subject, correct the behavior and retest.
IncompleteThe engine could not reach a conclusive result.Record what needs human review; do not relabel it as a pass.
PassA supplied automated evaluation passed for its scope.Keep the evidence; continue the relevant manual checks.
InapplicableThe supplied rule did not apply in this scope.Keep it separate; it is not a pass for a particular subject.

Count rules and affected nodes explicitly

One missing-label rule can contain two affected input nodes. That is one rule and two node occurrences, not two independent rule types. Workbench preserves both counts so a filter does not silently change their meaning.

Counts describe the records supplied by the report. A producer may omit detailed pass nodes, or capture only part of a page. A zero-finding array does not prove that navigation, scanning or human review completed successfully.

Raw source HTML, selector text and failure messages are discarded during normalization. This reduces what can enter an export. It also means the minimized finding cannot reconstruct every diagnostic detail from the original scanner.

Turn the observation into a check

For a form finding, try the corrected and intentionally broken examples, submit invalid synthetic data, and check whether you can discover the relevant error and recover. For a dialog finding, check opening focus and focus return as well as the accessible name.

Axe can help find structural failures. A keyboard assertion can measure focus movement. Neither means that someone listened to a screen reader or understood the interface. Keep any unperformed manual check marked not-run.

Verify the behavior

Run from the repository root after the documented dependency and browser setup.

npm test
npm run test:e2e

Expected evidence: Core tests preserve separate outcome counts; browser tests exercise sample inspection and a supported raw axe import.

Manual review: Describe the selected state, rule and subject in your own words. Record any unresolved interpretation as a manual observation rather than a scanner pass.

These are reproduction instructions, not a claim that a command or human session passed. See the actual verification record for observed results.
